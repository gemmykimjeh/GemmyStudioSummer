The problem

A language model does the 500th task exactly as badly as the 1st.

It has no memory between jobs. Every mistake it makes, it is free to make again tomorrow.

BASELINEStock ACE — the control arm, never modified

Three specialists, one notebook.

Every task passes through the same three roles. Only the middle one ever sees whether the work was any good.

TASK IN→ 1 · GENERATOR
does the work→ GRADER

writes the lesson→ 3 · CURATOR

1 · Generator

Reads the notebook, does the actual customer work.

IN
  • playbook (full text)
  • question — the task
  • context — output guidance
  • reflection → always "(empty)"
OUT
  • JSON: reasoning
  • JSON: bullet_ids — which notes it used
  • JSON: final_answer ← graded

2 · Reflector

Post-mortem. Compares the work to the score and writes the lesson.

IN
  • question + the answer given
  • grading criteria (stands in for truth)
  • score + which criteria were missed
  • the notes the Generator cited
OUT
  • error_identification
  • root_cause / correct_approach
  • key_insight
  • bullet_tags — helpful / harmful / neutral per note

3 · Curator

The only role allowed to edit the notebook.

IN
  • the Reflector's whole verdict
  • current playbook + statistics
  • token budget
OUT
  • operations: [ ADD ]
  • section + content per note
  • DELETE / UPDATE exist in the schema but are not implemented — silently dropped

Two facts about the baseline that shaped everything after

1. The notebook is the only memory. There is no Reflector→Generator arrow — that input is wired but permanently empty. If a lesson does not make it into the notebook as text, it is lost.
2. The notebook can only grow. ADD is the only working operation. Stock ACE physically cannot remove a bad note. This single gap causes most of what goes wrong in slides 11–13.

The notebook, concretely

Everything the system "learns" is one line of English.

This is a real note from a real run. There is nothing else — no weights, no embeddings that matter, no hidden state.

How we measure

GDPval — 100 real professional tasks, graded against human-written checklists.

The benchmark

  • GDPval — tasks drawn from actual occupations: financial models, legal memos, clinical summaries, government filings.
  • No single right answer. Instead each task ships a human-written checklist of criteria with point values.
  • We run the first 100 tasks of the train split — full runs are too slow and too expensive on free-tier quota.
  • Model: gemini-3.1-flash-lite, temperature 0, free tier. Same model for every arm.

The three arms we always compare

  • Baseline ACE — the published framework, untouched. Our control.
  • Pure LLM + tools — one raw model call, no notebook at all. This is the ceiling reference: if our scaffolding cannot beat a bare prompt, the scaffolding is not earning its cost.
  • FBL — our feedback loop, the version under test.
Why "pure LLM" is in every chart: it is the honest opponent. A learning system that scores below a single unassisted prompt is a system that is subtracting value, no matter how much it improved against its own earlier self. We kept this arm in deliberately, and for several versions we were losing to it.

Why this benchmark

We chose GDPval for speed, knowing exactly what it would cost us.

This was a deliberate trade, made up front: pick the benchmark that lets us check direction fastest, and accept that it under-measures the thing we are actually building.

Why GDPval — it is light and it is fast

  • ~1 hour for a full 100-task run, at $0. Free-tier quota, small model, no GPU, no Docker.
  • That speed is the reason six versions exist. We could run, read the failures, change one thing, and re-run within a day. Dozens of runs in twelve days.
  • It answers "are we going the right way?" in hours, not weeks. Every decision in this deck was checked against a real measurement before we moved on.
  • Scoreable without ground truth — each task ships a human-written checklist, so we get a number on open-ended professional work.

What GDPval structurally cannot show us

  • Every task is a single shot. One prompt in, one deliverable out — no multi-step trajectory, no tool loop, no second attempt within a task.
  • That is the worst case for a notebook. Its whole premise is accumulating reusable procedure across repeated interaction; one-shot gives that premise the least possible leverage.
  • So our numbers answer the smaller question. "Does the notebook help write a better document?" — yes. "Does the notebook architecture work?" — still unanswered.

Counterpoint — and the honest state of the Terminal-Bench run

  • The 21 % is not yet a usable result. Harness limits, not agent ability, dominate: output_truncated on 9 of 14 tasks, step_budget ×2, bash_timeout ×2, setup_error ×2. Tasks failed at 8/9 and 9/11 tests passing — that is our plumbing, not the agent.
  • Should we have started here instead? At Terminal-Bench's cost per run we would have managed two or three iterations, not six versions — and would likely have found none of the disclaimer family, the rubric contamination, or the growth-gate result.
  • The trade in one line: speed bought us the failure catalogue; Terminal-Bench must now buy us the architectural verdict.
Read this before any number in this deck

The measuring stick changed twice. Scores are only comparable inside an era.

This is the most important caveat in the deck. Anyone comparing v4's 0.631 to v5's 0.604 and concluding "v5 was worse" has been misled by the instrument, not the system.

The proof it was the instrument

The baseline arm never changed a line of code between E2 and E3. Its score still moved 0.5306 → 0.5159. That −0.015 is purely the grader ceasing to hand out credit for deliverables that did not exist. Every arm dropped for the same reason.

Counterpoint — we could have been accused of moving the goalposts

Changing a benchmark mid-project is exactly what a team does when it wants friendlier numbers. Our defence is that the change made every arm score lower, including ours — and that we re-ran the untouched control to prove it. Had we tightened the grader and only our own score went up, the result would be worthless.

BASELINEJul 15 · failure analysis of the 22 zero-scoring tasks

Before changing anything, we read every task the baseline scored zero on.

Three patterns accounted for nearly all of them. Each one became a decision later in this deck.

Observed failureWhat the agent actually didBecame
1 · Could not open the attachment, so it invented the data Task ships a spreadsheet. Agent has no file tool, cannot read it, and rather than stopping it simulates plausible-looking numbers. Every figure is wrong. → v5 file I/O

Note on where failure #2 came from — this was self-inflicted

The under-length problem traced back to one of our own hand-written starter notes: "Match the form and depth of the output to what the task and audience actually need; more content is not automatically better."

Perfectly sensible writing advice. Given to a model being graded on checklist coverage, it is an instruction to omit things. We wrote it, and it cost us across every task. The seed notes are as dangerous as the learned ones.

v1Jul 13–14Research-led — no defect prompted this

Split the notebook in two, and add a gatekeeper.

The first version was not a response to a bug. It was assembled from four papers, before we had run anything.

Why — four papers, four borrowed ideas

  • ReasoningBank (2509.25140) — agents can distil strategy from failures, not just successes. Stock ACE only learned from what worked. → learn "what not to do" too.
  • AEL (2604.21725) — separate concrete know-how from abstract cross-task patterns; use a Thompson bandit to pick which to read. → two notebooks + a selector.
  • EDV (2606.24428) — verify before you write to memory; default to reject. → a 4th agent, the Verifier.
  • ASSAY — start from hand-written immutable templates rather than an empty page. → ~21 protected seed notes.
  • Self-Grounded Verification (2507.11662) — LLMs grade themselves far too generously; ground the checklist in the task first. → shaped how we fed the grader's verdict back in.

What changed vs baseline

  • Two notebooks — concrete (specific techniques) and abstract (general principles), edited independently.
  • Thompson selector — a bandit decides which single notebook the Generator reads on each task.
  • Reflector runs twice — one concrete-flavoured pass, one abstract pass.
  • Verifier added — 4th agent, sits between Reflector and Curator. Rejects notes that are untrue to the trajectory or wrongly-levelled.
  • Two Curators, one per notebook.
  • Seeded start — ~21 protected notes instead of an empty page.

  • Honest reading of v1: direction encouraging, magnitude unknown.
v2Jul 15–16Cost-driven + defect-driven

Delete the machinery that was not paying for itself.

Why

  • The Verifier rejected 0 bullets in 100 tasks. Pure token cost, no decisions. Its job was already being done by the Curator's own novelty filter.
  • The Thompson selector was solving a problem we invented. Showing the Generator only one of two notebooks meant deliberately hiding half our memory on every task.
  • Per-task abstraction is incoherent. You cannot extract a cross-task pattern from a single task. AEL's original idea aggregates across episodes; we were calling it once per episode.
  • Cost was ~1.8× baseline for +0.025. That ratio does not survive contact with a customer.

What changed

  • Verifier removed. 4 agents → 3.
  • Thompson removed. Generator now always reads both notebooks as one labelled two-part view.
  • Reflector's 3 prompts collapsed into 1 — concrete insight, abstract insight and helpful/harmful tagging now come back from a single call.
  • Two-timescale learning — concrete updates every task; abstract updates once per 5 tasks, from a buffered window of 5 real trajectories.
  • Seed rewrite — the "more content is not automatically better" note replaced with "under-delivering on length is as much a failure as missing a section."

Why it was unstoppable — the arithmetic

We counted every operation the Curator ever issued across the project: 2,189 ADD versus 39 DELETE. The loop adds roughly 56 notes for every 1 it removes — and in stock ACE, DELETE did not work at all. The disclaimer rule was independently re-derived on tasks 7, 12, 20 and 26. Deleting it once was never going to be enough.

The mechanism, in one line

Hedging is a locally rational strategy. On any single task, refusing carefully looks safer than attempting and failing. The Reflector, seeing a mediocre-but-not-zero score, tags the hedge helpful. The counter climbs. Nothing in the system ever measures what the agent could have scored by simply trying.

helpful=43 — the loop reinforced its own refusal forty-three times.

v3Jul 16Defect-driven

Teach the post-mortem what "good" actually means.

Why

  • v2 scored below the pure-LLM baseline. Diagnosis: the Reflector had learned that "if we don't have a sure answer, write down that I'm not sure" — and the rubric judge scores hedging as failure.
  • The Reflector was writing lessons while blind to the grader's actual reasoning. It could see a number, not why points were lost.

What changed

  • Seed notes rewritten to forbid hedging outright, e.g. err-00009: "Retrieve before you hedge: if a value is in an attachment or reachable by tool, open it. Only after retrieval fails may you mark a value unavailable — and never replace a required value with commentary about it."
  • Reflector prompt rewritten to ban recommending capability disclaimers.
  • Reflector and Curator now read the grader's per-criterion reasoning, not just the score — so lessons align with what was actually penalised.

v2 – v3Second self-inflicted class

The notebook started optimising for a document it had never seen.

The Reflector can see the grading checklist. The Generator cannot — it never has. So every note below is an instruction the working agent is physically unable to follow.

VersionWhat the loop wrote — verbatim

Why this is worse than it looks

  • These notes are not merely useless — they displace useful notes in a fixed token budget.
  • At peak, 62 notes in the notebook referenced a rubric the Generator never receives.
  • They push the model toward describing compliance instead of producing the deliverable — the exact failure mode from slide 7.

The general lesson we took

Whatever you show the Reflector, it will write instructions about — even about things the Generator cannot see. The two agents have different views of the world, and the learning loop does not know that. Every input we grant the Reflector is a new category of unfollowable advice we have just authorised.

This class was measured and eliminated in later work; the mechanism is documented here because it generalises to any customer deployment.

v4Jul 16Architectural reversal

Stop splitting the notebook. Split authority instead.

The single biggest structural change in the project — and it meant abandoning the idea v1 was built around.

Why

  • The concrete/abstract split had produced no measurable benefit across v1–v3, while doubling the surfaces where bad notes could accumulate.
  • Every failure so far shared one root cause: a learned note overriding a rule we actually cared about. No note was ever safe from being contradicted by a later note.
  • The JSON output wrapper was truncating long deliverables — the extractor needed a hand-rolled recovery path for broken JSON, and answers stayed shorter than pure LLM's.

What changed

  • Two notebooks → one notebook + one RULEBOOK. The rulebook is 27 hand-written rules that no agent may ever add to, edit, or delete. It carries no counters. It is injected last into all three prompts, and outranks everything.
  • DELETE implemented for real — the Curator can finally remove a note, with a written reason.
  • JSON wrapper dropped. The Generator's entire response is the deliverable; cited notes move to a trailing CITED: [id] line.
  • Standing cleanup orders — the Curator is permanently instructed to hunt down capability-disclaimer notes and rubric-referencing notes.

v4Receipts — what the Generator is literally told

The Generator prompt, before and after.

Baseline ACE · output format

Your output should be a json object, which contains the following fields: - reasoning: your chain of thought / reasoning / thinking process, detailed analysis and calculations - bullet_ids: […] you should include their bullet_id in this list - final_answer: your concise final answer

**Answer in this exact JSON format:** { "reasoning": "…", "bullet_ids": ["calc-00001"], "final_answer": "[Your concise final answer here]" }

Ours · output format

- Plan briefly in your head, but DO NOT print any planning or scratchpad. Your output is the deliverable only. - Your ENTIRE output IS the deliverable: the COMPLETE actual work product (document, table, analysis, memo, …) written IN FULL at professional length — never a summary, outline, plan, or hedge. If the task implies a long document, write the long document.

- CITATION LINE: after the deliverable, on the VERY LAST line, list the bullet_id of every bullet you actually used […] prefixed with `CITED:`. This line is NOT part of the deliverable; it is stripped before grading.

Effect   The word concise was instructing the model to under-deliver on a benchmark that scores checklist coverage — failure mode #2 from slide 08, written into the prompt itself. Removing the JSON envelope also removed the truncation that had required a hand-rolled broken-JSON recovery path. Average deliverable went 2,170 → 3,688 chars.

Baseline ACE · how to treat the notebook

- Read the playbook carefully and apply relevant strategies, formulas, and insights - Pay attention to common mistakes listed in the playbook and avoid them

That is the entire instruction. There is no notion of some guidance outranking other guidance — every note carries equal authority, including the ones the loop wrote about its own inability to do the job.

Ours · two tiers of trust

**How to read what you are given — two blocks by TRUST level:** - **RULEBOOK** (at the END) — immutable, must-follow ground rules. Hard constraints: violating any one fails the task, and they take precedence over everything above. - **LEARNED PLAYBOOK** (above, if present) — hints extracted from PAST tasks […] some may not fit this task, so use judgment and ignore any that don't apply. All are advisory. On conflict, a RULEBOOK rule beats any learned hint.

Effect   This is the sentence that made the disclaimer family survivable. Before it, a self-written note saying "you must open with 'I am unable to generate binary files'" had exactly the same standing as a hand-written rule forbidding it. Afterwards, the rulebook wins by construction.
Also added to the Generator, no baseline equivalent — a completeness clause ("extract every distinct thing it asks for … each named party, role, approver, field, step, category … Enumerate; do not sample, generalize, or cover a set with one representative case") and a file-vs-prose decision rule making the wb.save('output.xlsx') line mandatory — "A script that only computes or print()s WITHOUT a save call produces NO file and scores ~0."
v3 → v6Receipts — what the Reflector and Curator are told

The learning prompts, before and after.

Baseline · how to tag a note

- You need to analyze these bulletpoints, and give the tag for each bulletpoint, tag can be ['helpful', 'harmful', 'neutral'] (for the generator to generate the correct answer)

No definition of what earns each tag. In practice the model tagged by outcome: the task scored well, therefore the notes it cited were helpful. That is how fmt-00037 reached helpful=43.

Ours · tag by causation, not by outcome

- Tag each provided bulletpoint by its ACTUAL causal effect on THIS deliverable — NOT by whether the task passed overall. Mark 'harmful' if the bullet steered the deliverable toward a missed or penalized criterion, wasted effort, or crowded out a required element — even on a high-scoring attempt. Mark 'helpful' only if it demonstrably improved a graded element. A bullet merely being present on a passing task is NOT evidence that it helped.

Effect   Paired with the score-weighted counters and a harmful floor of 0.25, this is what finally let a bad note lose points on a task that nonetheless passed — the exact loophole the disclaimer family had been living in.

Baseline · what the Curator may do

**Available Operations:** 1. ADD: Create new bullet points with fresh IDs - section: the section to add the new bullet to - content: the new content of the bullet […]

One operation. Removal is never mentioned, and the DELETE handler is an unimplemented stub — so the notebook was structurally incapable of shrinking.

Ours · two standing cleanup orders

**STANDING WARNING — do NOT (re)learn capability-disclaimer bullets:** […] NEVER ADD a bullet that advises the writer to state it "cannot" / "is unable to" produce a file […] These FEEL helpful but LOWER the score […] MAINTENANCE (cleanup): scan the CURRENT playbook shown above. For every EXISTING non-protected bullet that matches the pattern above, emit: {"type": "DELETE", "bullet_id": "…", "reason": "capability-disclaimer bullet"}

**STANDING WARNING — never write the word "rubric" into a bullet:** The agent that reads this playbook NEVER sees a rubric or grading criteria […] Any bullet containing the word "rubric" is deleted automatically, so adding one wastes the slot.

Effect   The Curator is now told to hunt, not just to file. Across the project it issued 2,189 ADD against 39 DELETE — those 39 exist only because of this block, and most cite the same root cause verbatim: "capability-disclaimer bullet".

A failure that nearly cost us a wrong conclusion

On Jul 17 every gold reference answer suddenly graded 0.000. We came close to concluding "the harness under-credits even perfect answers." The real cause was WinError 10061 — the grading proxy had died, and the harness was silently scoring 0 instead of raising the error. That silent-failure path is still unpatched and remains a live risk to every number we produce.

Counterpoint — why fixing the ruler mid-project was still the right call

  • The alternative was worse. Every earlier score was measured against an instrument that rewarded pretending. Continuing would have meant optimising the agent to exploit a broken judge — numbers rising while the product got worse.
  • The cost is real: Era 2 and Era 3 numbers cannot be compared, which is why this deck reports them as two panels rather than one rising line.
v5Jul 17–20Closes failure mode #1 from slide 7

Give it real files, then make it prove the code runs.

Why

  • Failure mode #1 — the agent could not open attachments, so it fabricated data. Every derived figure was wrong.
  • Even with file access, the model would inline a summary of a spreadsheet rather than reading the actual source.
  • Generated code that crashed still left a stub file behind and was counted as success.

What changed

  • Source-file manifest — the task text now names the real on-disk filenames, so generated code can call pd.read_excel('source.xlsx').
  • Rule rb-fmt-08 — read the source file, never inline a summary of it.
  • Execute-and-repair loop — run the code; on failure feed the traceback and the real data schema back and let it fix itself, up to 2×.
  • Independent-path self-verify (rb-chk-01) — check the answer by a second, different route.

v6Jul 20Colleague's proposal — Yusif

Learn from what went wrong. Never from what went right.

Why

  • Slide 11's arithmetic: the loop adds ~56 notes for every 1 it deletes. Growth was the disease.
  • A high score is not evidence that the cited notes helped. They were merely present. Yet the Curator still added new notes on every success — encoding whatever the model happened to do that time.
  • This is exactly how fmt-00037 reached helpful=43.

What changed — one threshold

  • If a task scores above 0.75, the Curator is skipped entirely. The notebook may not grow.
  • Everything else still runs on those tasks: reflection, helpful/harmful tagging, and the mechanical prune of net-harmful notes.
  • Counters became score-weighted floats with a harmful floor of 0.25 — so an explicit harmful tag still bites even on a passing task. This exists specifically to stop the fmt-00037 pattern.
  • 38 of 100 Curator calls skipped.

Counterpoint — three things this result does not yet prove

1. 0.75 is arbitrary. We tested one threshold, once. 0.6 or 0.9 may be better; we have no curve.

Honest status

What we can defend, and what we cannot.

Defensible today

  • +0.113 over the untouched baseline and +0.041 over a bare LLM prompt, on the same 100 tasks, same model, same grader.
  • Zero-scoring tasks cut from 22 → 4. The reliability story is the strongest one we have and it held across every era.
  • We found and fixed six distinct classes of self-inflicted damage — the disclaimer family, rubric-chasing, hedging, placeholder contradictions, corrupt counters, and unbounded growth. Each is documented with the verbatim text.
  • Restricting learning improved results — v6 scored higher on a 29 % smaller notebook and 22 % fewer tokens. This is a genuinely non-obvious finding.

Not yet defensible

  • Generalisation is unproven. v2–v6 were tuned against the same 100 tasks used to score them. A held-out slice has not been run.
  • Almost no statistics. Only one comparison in the project carries a p-value. Most version-to-version deltas are within run-to-run noise.
  • Rulebook vs learned notebook is not separated. We cannot currently say how much of the gain is 27 hand-written rules versus anything the system learned by itself.
  • Single runs. v6's headline number has no reproducibility estimate.
  • A silent-failure path remains in the harness — a dead grading proxy still scores 0 rather than raising.

The framing that survives scrutiny

The strongest claim we can make is not "the loop makes the agent smarter." It is: "we built an agent that reliably produces real deliverables instead of descriptions of deliverables, and in doing so we mapped six specific ways a self-improving memory damages itself — with the verbatim evidence for each."

That second claim is more useful commercially anyway. Every one of those six failure modes will appear in any customer deployment of this idea, by us or by a competitor.

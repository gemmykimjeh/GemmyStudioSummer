## 0. 전제와 한계 — 먼저 읽을 것

**측정한 것은 GAIA 165건뿐이다.** 아래 제안 중 벤치마크 일반화 부분은 **구조적 논증이지
측정 결과가 아니다.** TB2·SWE-bench·GDPval에서 같은 병목이 지배적인지는 확인하지 않았다.

§7에 **API 비용 없이 이를 검증하는 절차**를 넣었다. 제안을 실행하기 전에 §7을 먼저 돌리는 것을
권한다. 만약 §7의 결과가 GAIA와 다르면 **제안을 벤치마크별로 갈라야 한다.**

## 1. 우리 벤치마크 셋은 출력 양식이 세 갈래다

| 양식 | 벤치마크 | 종료 시점 | 채점 방식 |
|---|---|---|---|
| **값-응답** | GAIA · BrowseComp · simple-evals | 문자열 제출 | exact match |
| **상태-변경** | **TB2** · SWE-bench · tau-bench · OSWorld · AutomationBench | 환경이 목표 상태 도달 | 테스트 실행 |
| **산출물-판정** | **GDPval** | 문서 제출 | LLM 심사 |

이 구분이 중요한 이유: GAIA 분석에서 자연스럽게 나오는 처방(예: "답 문자열을 타입 필드로")은
**TB2에 답 문자열이 존재하지 않으므로 죽은 코드가 된다.** 양식에 걸리지 않는 층에서 고쳐야 한다.

---

## 2. 세 양식을 관통하는 하나의 실패 — 검증 없는 종료

세 양식 모두 에피소드가 **에이전트의 "끝냈다" 선언**으로 종료된다. 그 선언이 현재 **아무 책임도
지지 않는다.**

```
GAIA        답을 찾았다고 선언  →  출처 확인 없음          →  'Jerome Wiesner' (그럴듯한 오답)
TB2         구축했다고 선언     →  채점자 방식으로 미검증  →  테스트 실패
SWE-bench   고쳤다고 선언       →  스위트 미실행           →  회귀 발생
tau-bench   처리했다고 선언     →  최종 DB 상태 미확인     →  규칙 위반 잔존
GDPval      완성했다고 선언     →  brief 요구사항 미대조   →  항목 누락
```

### GAIA에서 관측된 근거

| 지표 | 정답(중앙값) | 오답(중앙값) |
|---|---|---|
| 스텝 수 | 10 | 28 |
| 브라우저 호출 | 0 | 9 |
| 헤지 표현 | **0 / 116** | **10 / 49** |

```
스텝 구간별 정답률
   0~10 : 85.0%      20~35 : 54.1%      60+  : 33.3%
  10~20 : 81.2%      35~60 : 29.4%      ← 20스텝 이후 평평
```

**20스텝 이후 노력이 정확도로 환전되지 않는다.** 그리고 헤지 표현이 정답에서 0건이라는 것은
**에이전트가 자신이 모를 때를 알고 있으나 그 신호가 출력 경계에서 폐기된다**는 뜻이다.

병목은 계획도 도구도 아니라 **믿음을 관리하는 층의 부재**다.

## 3. 제안 1 — 책임 있는 종료 🔴 최우선

**파일:** `openhands-sdk/openhands/sdk/tool/builtins/finish.py:21`

### 현재

```python
class FinishAction(Action):
    message: str = Field(description="Final message to send to the user.")
```

종료 선언에 담기는 정보가 자유 텍스트 한 덩어리뿐이다.

### 제안

```python
class FinishAction(Action):
    message: str

    # ── 전 벤치마크 공통 ──────────────────────────────
    verification: str = Field(
        description="What you actually ran or checked to confirm this is correct. "
                    "Report what you executed, not what you believe.")
    unverified: list[str] = Field(
        default_factory=list,
        description="Claims or requirements you could not check.")
    confidence: Literal["high", "medium", "low"] = "medium"

    # ── 값-응답 벤치마크에서만 사용 ──────────────────
    final_answer: str | None = Field(
        default=None,
        description="Direct answer with no surrounding prose.")
```

### 왜 이 형태인가

핵심은 `final_answer`가 아니라 **`verification` / `unverified` / `confidence`** 세 필드다.
이들은 출력 양식과 무관하게 의미를 갖는다.

| 벤치마크 | `verification`에 들어갈 내용 |
|---|---|
| GAIA | "출처 URL X에서 확인, 독립 출처 Y로 교차확인" |
| **TB2** | "`pytest tests/` 실행 → 12 passed" · "`curl localhost:8080` → 200" |
| SWE-bench | "전체 스위트 실행, 회귀 없음" |
| tau-bench | "최종 DB 상태 조회 결과 첨부" |
| GDPval | "brief의 요구사항 7개를 섹션별로 대조" |

### 상태-변경 벤치마크에서 오히려 강력한 이유

GAIA에서 "출처를 댔다"는 주관적이다. 그러나 TB2·SWE-bench에서는 `verification`에 적힌 명령을
**하네스가 실제로 재실행해 대조할 수 있다.** 거짓 검증 주장이 자동으로 검출된다.

### 부수 효과 — 기권 채널

`confidence`가 "모르겠다"를 표현할 수 있는 유일한 통로가 된다. 현재는 에이전트가
*"unable to access…"* 라고 **명시적으로 실패를 선언하고도** 답변란을 채운다(`0b260a57`).
캘리브레이션이 내부에 존재하는데 인터페이스가 받지 못하고 있다.

### 하위호환

`verification`에 기본값을 주면 기존 코드는 그대로 동작한다. 벤치마크 어댑터는 있으면 쓰고
없으면 `message`로 폴백한다.

**비용:** 며칠 · **위험:** 낮음 · **적용:** 전 벤치마크

## 4. 제안 2 — 검증된 주장 원장 (무효화 추적 포함) 🔴 핵심

현재 `ConversationState`는 이벤트 나열만 보유한다. 구조적 상태를 추가한다.

```python
class VerifiedClaim(BaseModel):
    claim: str                      # "port 8080 responds" / "test_auth passes"
                                    # / "출처 X가 Y를 진술함"
    check: str                      # 확인에 사용한 명령·URL (재실행 가능한 형태)
    checked_at_step: int
    outcome: str
    invalidated_by: str | None = None   # 이후 어떤 행동이 이를 무효화했는가

class ConversationState:
    claims: list[VerifiedClaim] = []
```

에이전트는 `record_claim` / `recheck_claim` 도구로 이를 조작한다.

### 무효화 추적이 이 제안의 일반화 지점

GAIA에는 없고 상태-변경 벤치마크에만 있는 차원이다 — **주장이 시간이 지나며 상한다.**

| 벤치마크 | 원장이 잡아내는 것 |
|---|---|
| GAIA | 근거 없는 주장, 교차확인되지 않은 중간 홉 |
| **TB2** | **앞서 통과한 테스트를 이후 설정 변경이 깨뜨림** |
| SWE-bench | 내 패치가 다른 테스트를 깨뜨림 (회귀) |
| tau-bench | 앞 턴에서 확인한 DB 상태를 뒤 턴 조작이 무효화 |
| GDPval | 초안에서 충족한 요구사항이 개정 과정에서 누락 |

원래 GAIA 분석에서는 "근거(evidence) 원장"이었으나, 무효화 차원을 넣으면 **더 일반적이면서
동시에 더 강력해진다.**

### 이것이 해소하는 것

| 현재 불가능 | 원장이 있으면 |
|---|---|
| "이 주장의 근거가 무엇이었나" | 조회 가능 |
| "독립 출처로 확인했는가" | 재확인 횟수 집계 |
| 압축 후 출처 보존 | 원장은 요약 대상에서 제외 (제안 3) |
| 근거 기반 종료 판단 | "모든 주장이 유효한가"로 판정 |
| 중간 홉 오류 감지 | 홉별 근거를 되짚을 수 있음 |

**비용:** 몇 주 · **위험:** 중간 · **적용:** 전 벤치마크

## 5. 제안 3 — condenser가 원장을 지우지 않게 🔴 TB2에서 특히 중요

**파일:** `openhands-sdk/openhands/sdk/context/condenser/llm_summarizing_condenser.py`

```python
max_size: int = 240      # 이벤트 240개 초과 시 발동
keep_first: int = 2      # 앞 2개는 절대 요약하지 않음
```

발동하면 뒤쪽 절반을 LLM 요약으로 접는다. 이때 **어떤 주장이 어느 출처에서 나왔는지가
산문으로 뭉개진다.**

### 왜 TB2에서 더 심각한가

터미널 작업은 빌드 로그·스택트레이스가 폭발하여 **압축이 훨씬 자주 발동한다.**
그 결과 "이미 시도해서 실패한 것"이 요약에 흡수되고, **에이전트가 같은 시도를 반복한다.**

GAIA에서는 다단계 문항(Level 3, 53.8%)에서만 문제였으나, 상태-변경 벤치마크에서는
기본 실패 모드가 된다.

### 제안

`keep_first`와 같은 방식으로 **`claims` 원장을 요약 대상에서 영구 제외**한다.
압축이 일어나도 "무엇을 확인했고 무엇이 아직 유효한가"가 보존된다.

**비용:** 며칠 · **위험:** 낮음 · **적용:** 전 벤치마크 (TB2·SWE-bench에서 최대)

## 6. 제안 4 — 진행 없는 반복을 전략 전환 트리거로 🟡

**파일:** `openhands-sdk/openhands/sdk/conversation/stuck_detector.py`

이미 존재하는 자산이다. 반복 행동·독백·교대 패턴을 감지한다.

```python
MAX_EVENTS_TO_SCAN_FOR_STUCK_DETECTION = 20
# 감지 항목: action_observation 반복, action_error 반복,
#            agent monologue, alternating pattern
```

**현재는 감지 후 `STUCK`으로 종료만 시킨다.** 감지 기계는 있는데 처분이 "포기"뿐이다.

### 제안 — 종료 대신 1회 개입 후 계속

```python
if detector.is_stuck() and not state.strategy_switch_injected:
    on_event(MessageEvent(source="environment", content=(
        "Your recent actions repeat without progress. Before acting again, state: "
        "(1) what you have established, with the check that confirmed it; "
        "(2) what remains unknown; "
        "(3) a different approach — not a variation of the current one.")))
    state.strategy_switch_injected = True
    # STUCK 으로 종료하지 않고 계속
```

### 벤치마크별 가치

GAIA에서는 브라우저 호출 중앙값이 정답 0회 / 오답 9회로, 표류의 증상이었다.
**상태-변경 벤치마크에서는 더 가치가 크다** — 빌드 실패 로그를 보며 같은 수정을
변주 반복하는 것이 전형적 실패이고, 게다가 거기서는 **진행 여부가 객관적으로 측정 가능하다**
(통과 테스트 수). 반복 감지에 더해 "테스트 통과 수가 N스텝간 증가하지 않음"을
조건으로 추가할 수 있다.

**비용:** 며칠 · **위험:** 낮음 · **적용:** 전 벤치마크

## 7. 제안 5 — 클린룸 검증 단계 🟡 상태-변경에서 최대

후보 완료 시점에 **깨끗한 상태**에서 검증을 다시 수행한다.

```
탐색 단계 → 후보 완료 선언
              ↓
검증 단계 : 새 컨텍스트 = (과제, 후보 결과, claims 원장)
            지시 = "채점자가 검증할 방식 그대로 검증하라"
              ↓
        통과 → 제출        실패 → 원장의 약한 고리로 복귀
```

### GAIA에서는 보이지 않는 실패 모드를 겨냥한다

상태-변경 벤치마크에는 다음 실패가 있다.

> **에이전트가 자기에게 유리한 방식으로 확인하고 종료한다.**
> 스위트 대신 테스트 하나만 실행하거나, 채점자와 다른 방식으로 서비스를 확인하거나,
> 자신이 만든 더러운 환경에서 통과를 확인한다.

따라서 검증 단계의 규칙은 **"채점자가 검증할 방식 그대로"**여야 한다.
TB2·SWE-bench는 테스트 명령이 존재하므로 **실제 실행이 가능**하고,
GAIA·GDPval은 근사만 가능하다.

### 근거

GAIA에서 20스텝 이후 정확도가 평평하다(35~60스텝 29%, 60+ 33%).
**추가 탐색이 정확도로 환전되지 않는다.** 같은 예산을 **검증에 배분하면**
환전될 가능성이 있다 — 이는 검증 가능한 가설이다(§9).

**비용:** 몇 주 · **위험:** 중간 · **적용:** 상태-변경 ≫ 값-응답

## 8. 폐기한 제안

GAIA 분석에서 처음 도출했으나, 벤치마크 셋 전반을 고려하여 철회한다.

| 폐기안 | 철회 이유 |
|---|---|
| `<BROWSER_TOOLS>` 문구 수정 | 브라우저 프롬프트 블록 내부이므로 TB2 경로에 걸리지 않는다. 같은 원칙("타이머가 아니라 검증으로 종료")을 **제안 1의 스키마에 넣으면 전 벤치마크에 적용**된다 |
| 열거 완결 프롬프트 | GAIA 수치 문항 전용. TB2·SWE-bench에서는 의미 없는 프롬프트 비대화 |
| `final_answer` 필수화 | 값-응답 전용. **선택 필드로 강등** |
| "원문 오타를 보존하라" 규칙 | **벤치마크 게이밍.** `Ploybius`→`Polybius` 건에서 에이전트는 옳게 행동했다. 이는 하네스가 명세할 문제이지 에이전트가 추측할 문제가 아니다 |

첫 번째 항목이 특히 중요하다. 프롬프트 한 줄 수정은 값싸 보이지만 **GAIA 경로에서만 작동한다.**
동일한 원칙을 종료 스키마에 넣으면 비용이 조금 늘고 적용 범위가 전체가 된다.

## 10. 일반화 검증 — API 비용 0으로 먼저 확인할 것

§0에서 밝혔듯 근거가 GAIA에 한정되어 있다. 제안 실행 전에 아래를 확인한다.

### 대상

TB2 실행 로그(우리가 직접 돌린 소수 실행 또는 tbench.ai 리더보드 제출본의 아카이브)

### 측정 항목

```
① 스텝 수 구간별 성공률
   → GAIA처럼 20스텝 이후 평평해지는가?
   → 평평하다면 "노력이 정확도로 환전되지 않는다"가 TB2에서도 성립

② 실패 에피소드 중 '테스트를 실행하지 않고 종료'한 비율        ← 가장 중요
   → 높다면 제안 1(책임 있는 종료)의 근거가 GAIA 밖에서 성립
   → 낮다면 TB2의 병목은 다른 곳이며, 제안을 벤치마크별로 갈라야 함

③ 통과했다가 이후 행동으로 깨진 테스트의 건수
   → 제안 2의 무효화 추적이 실제로 필요한지 확인

④ 최종 메시지의 헤지 표현 비율 (성공 vs 실패)
   → GAIA의 0/116 vs 10/49 패턴이 재현되는가
   → 재현되면 캘리브레이션 신호가 양식 무관하게 존재한다는 증거
```

**②가 판정 기준이다.** 이 값이 GAIA와 유사하게 높으면 제안 1~5를 그대로 진행한다.
낮으면 TB2의 실제 병목을 먼저 규명해야 한다.

## 11. 논문으로 쓸 경우

### 주장

> **에이전트 벤치마크는 탐색 능력을 측정하지 인식적 능력을 측정하지 않는다.**
> 병목은 스텝당 능력이 아니라 **믿음 관리 층의 부재**이며, 이는 출력 양식과 무관하다.

### 증거 (GAIA 165건)

```
0~10 스텝  85.0%          답이 바로 찾아지면 잘 푼다
35~60 스텝 29.4%
  60+ 스텝 33.3%          ← 평평. 노력이 정확도로 환전되지 않음

헤지 표현  정답 0/116 · 오답 10/49    캘리브레이션은 존재하나 폐기됨
브라우저   정답 중앙값 0 · 오답 9      실패 후 전략 전환 불가
Level 1/2/3  79.2 / 69.8 / 53.8%     홉당 ~90%의 곱셈 붕괴
```

### 반증 가능한 예측 — 논문의 힘은 여기 있다

> 제안 1·2·5를 적용하면 **≥20스텝 구간의 정확도만 상승하고 0~10스텝 구간은 변하지 않는다.**

"우리 방법이 +X점"보다 훨씬 강한 주장이다. 메커니즘을 특정하고 **어디가 오르고 어디가
오르지 않는지까지** 예측하므로, 틀리면 즉시 드러난다.

### 다중 벤치마크로 확장한 형태

같은 예측을 양식별로 구체화한다.

| 양식 | 예측 |
|---|---|
| 값-응답 (GAIA) | 장기 에피소드 구간에서만 정확도 상승 |
| 상태-변경 (TB2·SWE-b) | **"검증 없이 종료" 비율 감소가 성공률 상승을 매개**한다 |
| 산출물-판정 (GDPval) | 요구사항 누락 감소가 심사 점수 상승을 매개한다 |

매개(mediation) 관계까지 예측하면 단순 점수 비교보다 훨씬 강한 인과 주장이 된다.

### 부수 결과

출력 텍스트의 헤지 표현이 정확도를 예측한다(정답 0/116 vs 오답 10/49).
모델이 이미 무상으로 생산하는 캘리브레이션 신호를 인터페이스가 폐기하고 있음을
정량적으로 보인 결과이며, 그 자체로 작지만 깨끗한 발견이다.

## 12. ACE와의 관계

이 진단은 ACE 설계를 직접 제약한다.

- playbook이 **"어떻게 검색·조작할지"**를 축적하면 위 병목을 건드리지 못한다
- **"무엇을 믿을 수 있다고 판단했는지"** — 검증 절차, 교차확인 습관, 포기 조건 — 을
  축적해야 병목을 직접 겨냥한다
- **제안 2의 주장 원장이 그것을 담을 자연스러운 그릇이다.** ACE는 원장에 쌓인 패턴에서
  *"이 유형의 주장은 두 출처로 확인해야 한다"* · *"이 조작 뒤에는 테스트를 재실행해야 한다"*
  같은 규칙을 추출할 수 있다

즉 위 제안들은 OpenHands 개선안인 동시에 **ACE가 붙을 자리를 만드는 작업**이다.

### ACE 개선을 귀속하기 위한 계측기

| 관측 | 해석 |
|---|---|
| ≥20스텝 구간 정확도 상승 | 검증·전략 전환 개선 = **진짜 개선** |
| 0~10스텝 구간만 상승 | 쉬운 과제를 더 빨리 푼 것 |
| 헤지 비율 감소 + 정확도 상승 | 확신도 캘리브레이션 개선 |
| 산문형 답변만 감소 | 형식 순응 개선 — **추론 개선이 아님** |
| (TB2) 검증 없는 종료 비율 감소 | 책임 있는 종료의 내면화 |

마지막에서 두 번째 항목이 특히 중요하다. **ACE가 답변 형식만 개선해도 벤치마크 점수는
상승한다.** 추론 개선과 형식 개선을 분리하여 보고하지 않으면 결과의 해석이 무너진다.

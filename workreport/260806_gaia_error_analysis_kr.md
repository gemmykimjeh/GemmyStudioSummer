**대상:** GAIA-1 재현 풀런(2026-08-06)의 오답 **49건 / 165건**

**관련 문서:** `260806_..._delta.md`(환경) · `260806_..._results.md`(결과·하네스 9원칙)

| | 건수 | 특징 | 병목 |

## 1. 정답과 어떻게 다른가 — 6가지 유형

### 유형 A. 답이 아예 제출되지 않음 (12건)

최종 출력이 답이 아니라 **보고서**다.

```
gt   : '13'
ours : "After extensive research across Wikipedia's featured articles from 2022…"

gt   : '0.2'
ours : 'Based on my research, I found that: 1. **March 2021 paper**: Nicastro…'
```

12건 전부 `<solution>` 태그가 없다. 이 중 **3건은 본문에 정답을 갖고 있었다.**

```
872bfbb1  gt 'pears, bananas'   ours "…**Grapefruits, Pears, Bananas**…"
d5141ca5  gt '19/02/2009'       ours 본문에 날짜 존재
7a4a336d  gt '1:41.614'         ours 본문에 랩타임 존재
```

### 유형 B. 입도(granularity)가 다름 (5건)

정답을 알고 있으나 **얼마나 잘라 말해야 하는지**를 틀렸다.

```
gt 'THE CASTLE'         ours 'INT. THE CASTLE - DAY'      (앞뒤 수식 포함)
gt 'diamond'            ours 'crystalline diamond'         (수식어 추가)
gt 'Brunei, China, Morocco, Singapore'
                        ours '…, Venezuela'                (한 원소 초과)
gt '17'                 ours '17000'                       (단위 스케일)
gt 'egalitarian'        ours 'Egalitarianism'              (품사·어미)
```

### 유형 C. 원문을 "고쳐서" 틀림 (1건)

```
gt   : 'Picnic is in Ploybius Plaza.'
ours : 'Picnic is in Polybius Plaza.'
```

정답 쪽 `Ploybius`가 원문의 오타이고, 에이전트는 **철자를 바로잡아** 제출했다.
4스텝으로 끝난 쉬운 문항이었다. 정확히 읽고, 정확히 고쳐서, 틀렸다.

### 유형 D. 수량이 어긋남 (31건 — 최대 유형)

정답이 수치인 오답이 31건. 오차 폭이 두 갈래로 나뉜다.

**근접(계산 정밀도):**
```
0.0424 → 0.0429      17.056 → 16.919      85 → 90      +4.6 → +4.4
```

**대폭 이탈(열거 실패):**
```
55 → 194      60 → 2115      4 → 20      39 → 70      16000 → 12000
```

후자는 "전부 세어야 하는" 과제다. 에이전트는 표본을 보고 외삽한다.

### 유형 E. 엔티티가 바뀜 (11건)

```
gt 'Claude Shannon'  ours 'Jerome Wiesner'    (같은 MIT, 같은 시대, 같은 영상)
gt 'inference'       ours 'element'
gt 'backtick'        ours 'grave'             (grave accent = backtick, 동의어)
gt 'Rd5'             ours 'Nxc3'              (체스 수)
```

모두 **그럴듯한 오답**이다. 무작위가 아니라 근처의 다른 정답 후보를 골랐다.

### 유형 F. 목록의 원소가 어긋남 (7건)

```
gt 'Indonesia, Myanmar'      ours 'Myanmar, Timor-Leste'
gt 'Braintree, Honolulu'     ours 'Honolulu, Quincy'
```

`9318445f`가 상징적이다 — 긴 분수 수열에서 **앞 10항이 원본과 완전히 동일**하고 11항부터 갈린다.
게다가 **2스텝**만에 끝났다. 시작은 정확했고 끝까지 가지 못했다.

## 2. 에이전트 측면 — 왜 이런 답이 만들어졌나

### 2.1 궤적 통계

| 지표 | 정답(중앙값) | 오답(중앙값) |
|---|---|---|
| 스텝 수 | **10** | **28** |
| 비용 | $0.26 | $1.02 |
| 브라우저 호출 | **0** | **9** |
| 산문형 최종답 | 1/116 | 12/49 |
| 헤지 표현 | **0/116** | **10/49** |

```
스텝 구간별 정답률
   0~10 : 85.0%      20~35 : 54.1%      60+  : 33.3%
  10~20 : 81.2%      35~60 : 29.4%
```

> **주의:** 어려운 문제일수록 스텝도 많고 틀리기도 쉬우므로, 스텝 수는 난이도의 대리
> 지표이기도 하다. 인과로 단정할 수 없다. 다만 **20스텝 이후 평평해지는 모양**은
> 난이도만으로는 설명되지 않는다.

### 2.2 원인 ① — 검증 루프의 부재 (가장 근본)

루프는 `행동 → 관찰 → 판단`이며, 다음이 없다.

- 가설 추적 — "나는 X를 믿는다, 근거는 Y"
- 교차 검증 — "독립 출처가 X를 확인하는가"
- 확신도 — "답할 만큼 확실한가"
- 백트래킹 — "이 경로는 틀렸다, 다른 각도로"

결과적으로 에이전트는 **답이 생겼을 때** 멈추지 **근거가 생겼을 때** 멈추지 않는다.
정책 입장에서 *그럴듯한 답*과 *검증된 답*이 구별되지 않는다. 유형 E(엔티티 오류)가
전부 이 형태다 — `Jerome Wiesner`는 MIT·동시대·같은 영상 맥락에서 완벽히 그럴듯하다.

### 2.3 원인 ② — 실패 후 전략 전환 불가

브라우저 호출 중앙값이 정답 **0회** / 오답 **9회**다. 브라우저는 "검색으로 안 나왔다"의
증상이며, 꺼내 든 시점에 이미 대부분 진 상태다.

주목할 점: 우리가 커밋 핀으로 살린 `<BROWSER_TOOLS>` 프롬프트가 이 문제를 **인지하고 있다.**

> *"If 20+ total steps without converging, stop exploring and commit to your best answer."*

정확히 20스텝에서 꺾이는 것을 관측했으므로 **진단은 옳다.** 그러나 처방이
*"가진 것 중 최선으로 확정하라"*이다. 가진 것이 없을 때 이 지시는
**자신 있는 추측을 생산하라**가 된다. 유형 A(산문 12건)가 그 산물이다.

### 2.4 원인 ③ — 캘리브레이션을 만들고 버림

```
헤지 표현("unable to", "approximately", "based on my research")
  정답  0/116   ← 단 한 건도 없음
  오답 10/49
```

에이전트는 **자신이 모를 때를 안다.** 불확실성이 출력 텍스트에 그대로 드러난다.
그러나 답변 공간이 단일 문자열이라 **"모르겠다"가 결과가 될 채널이 없다.**
내부에 존재하던 신호가 출력 경계에서 폐기된다.

`0b260a57`은 극단적 사례다 — *"After conducting an extensive search using multiple
tools and approaches, I have been unable to access…"* 라고 **명시적으로 실패를 선언하고도**
답변란을 채웠다.

### 2.5 원인 ④ — 완전 열거를 못 함

정답이 수치인 오답 31건 중 대폭 이탈 사례(55→194, 60→2115, 4→20)는 모두
**집합 전체를 빠짐없이 세야 하는** 과제다. 에이전트의 탐색은 본질적으로 표본 추출이며,
"다 봤는가"를 판정하는 장치가 없다. `9318445f`의 앞 10항 일치가 이를 보여준다 —
방법은 옳았고 완주하지 못했다.

### 2.6 원인 ⑤ — 다단계 추론의 곱셈 붕괴

```
Level 1 : 79.2%      Level 2 : 69.8%      Level 3 : 53.8%
```

GAIA 난이도는 사실상 연쇄 홉 수다. 홉당 ~90%면 5홉은 0.9⁵ ≈ 59%로 Level 3 수치와 근접한다.
원인 ①이 여기서 증폭된다 — 중간 홉의 오류를 감지하는 장치가 없으면 첫 오류가 끝까지 전파되고
마지막에 **자신 있는 오답**이 나온다.

### 2.7 별도 무리 — 계산·판독 실패 10건

검색 0회·브라우저 0회, 터미널만 사용한 오답이 10건 있다.

```
50f58759(37스텝) · 6359a0b1 · e142056d · df6561b2 · cca530fc
4d51c4bf · 99c9cc74 · cca70ce6 · ded28325 · 9318445f
```

이들은 **데이터를 이미 손에 넣은 상태**에서 틀렸다. 탐색이 아니라 산술·판독·전사의 문제이며,
위 원인 ①~⑥과 병목이 다르다. `cca530fc`(체스)는 8스텝·검색 0회로, 실제 분석 없이 수를 제출했다.

### 2.8 한 문장

> **탐색은 하지만 검증은 하지 않는다.**
> 답이 쉽게 찾아지는 문제는 잘 풀고(0~10스텝 85%), 찾아지지 않는 문제에서는
> **더 오래 헤매다가 근거 없는 답을 확신 있게 제출한다**(35스텝 이상 29%).
> 병목은 계획도 도구도 아니라 **믿음을 관리하는 층의 부재**다.

## 3. 하네스 측면 — 9원칙 중 무엇이 오답을 야기했나

`results.md` §11의 9개 원칙을 오답 유형에 대응시킨다.

| 원칙 | 관여 | 해당 오답 | 크기 |
|---|---|---|---|
| §11.1 Typed egress | **직접 야기** | 유형 A 12건 중 정답 보유 3건 | −1.8%p |
| §11.2 출력 계약 명세 | **직접 야기** | 유형 B 5건 + 유형 C 1건 | −3.6%p |
| §11.3 부분 정규화 | **직접 야기** | `Egalitarianism`, `grave` 등 | (§11.2와 중첩) |
| §11.4 가변 환경 | **직접 야기** | 원본만 정답 11건 중 6건 | −3.6%p |
| §11.5 전제조건 단언 | **차단됨** | 0건 | — |
| §11.6 런타임 의존성 | **차단됨** | 0건 | — |
| §11.7 절대 타임아웃 | **차단됨** | 0건 | — |
| §11.8 구간 보고 | 해석에 영향 | 개별 오답 아님 | — |
| §11.9 통합 원칙 | 위 전부의 상위 개념 | — | — |

### 3.1 §11.1 — 타입 있는 출력 (직접 야기)

`<solution>` 태그는 자유 텍스트 안의 **소프트 계약**이며, 지키지 않아도 아무 일이 없다.
우리 12건 / 원본 10건이 위반했고 **양쪽 각 3건이 정답을 보유한 채 탈락**했다.

손실 폭이 양쪽 동일하다는 점이 중요하다 — 우리 환경 문제가 아니라 **하네스의 구조적 성질**이다.

**구조적 해법:** 답을 종료 도구의 타입 인자로 만든다(`finish(final_answer: str)`).
그러면 파싱 가능한 답 없이는 **물리적으로 종료가 불가능**해지고, 이 실패 모드가
정규식 개선이 아니라 설계로 사라진다.

### 3.2 §11.2 — 출력 계약이 과제의 일부 (직접 야기)

유형 B·C 전부가 여기 해당한다. 문항은 **필요한 입도를 명시하지 않는데** 채점기는
단일 정규형만 받는다. 그 결과 **능력과 형식 추측을 합산 측정**하게 되고, 실패 귀속이 불가능해진다.

유형 C(`Ploybius`→`Polybius`)가 극단적 증거다. 에이전트는 **원문을 정확히 읽고
합리적으로 교정한 뒤 탈락했다.** 이 문항에서 측정된 것은 능력이 아니라
"원문 오타를 보존하라는 암묵 규칙을 추측할 수 있는가"이다.

### 3.3 §11.3 — 부분 정규화 (직접 야기)

채점기는 대소문자를 흡수하지만(`Egalitarian` 통과) 어미는 처리하지 않는다
(`Egalitarianism` 탈락). `bacon`은 받으면서 `backtick`의 동의어 `grave`는 거부한다.

"표면형은 무관하다"는 신호를 준 뒤 **다른 표면형으로 처벌**한다. 경계가 문서화되어 있지 않아
**학습이 불가능**하다.

### 3.4 §11.4 — 가변 환경 (직접 야기)

원본만 맞춘 11건 중 6건이 웹 검색 결과의 시점 차이다.

```
gt 2018   원본 2018   우리 1987
gt 1927   원본 1927   우리 1915
gt +4.6   원본 +4.6   우리 +4.4
```

또한 우리 자체 실행 간에도 `c61d22de`가 False→True로 뒤집혔다(temperature 0.0).
**고정된 ground truth가 존재하지 않는다.**

### 3.5 §11.5~§11.7 — 차단되어 관여하지 않음

셋 다 이번 실행에서는 **0건**이다. 우연이 아니라 사전 조치의 결과다.

| 원칙 | 잠재 실패 | 사전 조치 | 방지된 손실(추정) |
|---|---|---|---|
| §11.5 전제조건 | MCP 사망 시 웹검색 없이 진행 | 컨테이너 내 JSON-RPC 핸드셰이크 검증 | 대규모 |
| §11.6 런타임 의존성 | `uvx mcp-server-fetch` 버전 미고정 → ImportError | 2025.4.7 + mcp 1.26.0 핀 | 대규모 |
| §11.7 절대 타임아웃 | ffmpeg 27초/30초, whisper 474초/120초 | 이미지 사전 설치 | mp3 3문항 등 |

검증 결과가 이를 뒷받침한다 — tavily 852회 **오류 0건**, ffmpeg 실패 0건,
mp3 정답률이 원본과 동일한 2/3.

**이 세 원칙은 "오답을 야기했다"가 아니라 "야기했을 것이나 사전에 막혔다"이다.**
막지 않았다면 그 손실은 능력 실패와 구분 불가능한 형태로 점수에 섞였을 것이다.

### 3.6 §11.2의 확장 — 기권할 수 없는 답변 공간

원칙 목록에 없던 사항이 이번 분석에서 드러났다.

에이전트는 불확실성을 **생산한다**(헤지 10/49). 그러나 답변 공간이 단일 문자열이라
**기권(abstention)이 표현 불가능**하다. 그 결과 캘리브레이션 신호가 출력 경계에서 폐기되고,
"모른다"가 "틀린 답"으로 강제 변환된다.

이는 §11.2(출력 계약)의 특수 사례로 볼 수 있으나, 처방이 다르다 —
형식을 명시하는 것으로는 부족하고 **답변 공간에 `unknown`을 포함**시켜야 한다.
`unknown` 제출을 오답과 동일 취급하되 별도 집계하면, 능력과 캘리브레이션을 분리 측정할 수 있다.

## 4. 정리

### 오답 49건의 귀속

```
하네스 설계 기인   약 10~11건 (≈20%, 점수로 ~6%p)
  §11.1 추출 실패      3건
  §11.2/§11.3 형식     6건
  §11.4 환경 변동     (원본 대비 차이의 주요 성분)

실질 능력 부족     약 34~38건 (≈80%)
  검증 부재 · 열거 실패 · 다단계 붕괴 · 계산 오류
```

### 에이전트에 필요한 것

계획이나 도구가 아니라 **믿음 관리(belief management)** 층:
가설 추적 · 교차 검증 · 확신도 · 포기 조건.

### 하네스에 필요한 것

§11.9의 통합 원칙 — **"에이전트가 틀렸다"와 "측정이 틀렸다"를 산출물 안에서
자동으로 구분 가능하게 만들 것.** §11.5~§11.7이 이번에 0건인 것은 우리가 세션의
상당 부분을 그 구분에 썼기 때문이며, 그 비용은 하네스 작성자가 한 번 치러야 할 것을
사용자가 매번 치르고 있다는 뜻이다.

### ACE 실험에의 함의

playbook이 **"어떻게 검색할지"**를 축적하면 위 원인 ①~⑤를 건드리지 못한다.
**"무엇을 믿을 수 있다고 판단했는지"** — 검증 절차, 교차확인 습관, 포기 조건 — 을
축적해야 병목을 직접 겨냥한다.

그리고 본 분석의 지표들이 **ACE의 개선을 귀속하는 계측기**가 된다.

| 관측 | 해석 |
|---|---|
| 20스텝 이상 구간 정답률 상승 | 검증·전략 전환이 개선됨 (진짜 개선) |
| 0~10스텝 구간만 상승 | 쉬운 문제를 더 빨리 푼 것 |
| 헤지 비율 감소 + 정답률 상승 | 확신도 캘리브레이션 개선 |
| 산문형 답변 감소만 | §11.1 형식 순응 개선 (추론 개선 아님) |

마지막 행이 특히 중요하다 — **ACE가 답변 형식만 개선해도 벤치마크 점수는 오른다.**
추론 개선과 형식 개선을 반드시 분리해서 보고해야 한다.
